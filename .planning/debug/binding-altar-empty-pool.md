## Current Focus

reasoning_checkpoint:
  hypothesis: "BindingAltarScreen#init() reads the candidate item slots (this.menu.getSlot(CANDIDATE_SLOT_BASE+i).getItem()) synchronously while building the TradeCandidateList widget, but on the CLIENT, ClientboundOpenScreenPacket (which triggers Screen construction/init()) and ClientboundContainerSetContentPacket (which actually populates the client-side menu's slot contents, including the candidate slots) are two SEPARATE packets processed in order. init() always runs to completion (synchronously, inside the open-screen packet handler) BEFORE the content-sync packet is even received, let alone processed — so every real player-driven open reads all-empty candidate slots and permanently bakes an empty TradeCandidateList, even though the server rolled a real, non-empty pool."
  confirming_evidence:
    - "BindingAltarMenu's CLIENT constructor path (IMenuTypeExtension.create(BindingAltarMenu::new) -> extraData ctor -> core ctor) calls resolveDisplayedCandidates(), which returns List.of() immediately because level.isClientSide() is true (see that method's own doc comment: 'On the CLIENT, this always returns an empty list ... vanilla's own container-sync protocol fills in the real per-slot item stacks immediately after open') — so the CLIENT's own menu instance starts with all candidate slots literally empty at construction time, same instant BindingAltarScreen's init() runs."
    - "BindingAltarScreen.init() (line ~76-83) builds `candidates` by reading this.menu.getSlot(...).getItem() ONCE, synchronously, inside init() — and passes that immutable list into `new TradeCandidateList(...)`, which is never rebuilt afterward. There is no containerTick()/slot-change hook wired up at all."
    - "Server-side, ServerPlayer#openMenu sends ClientboundOpenScreenPacket first, THEN calls initMenu()/addSlotListener() which triggers the container's full-content broadcast (ClientboundContainerSetContentPacket) as a SEPARATE packet — the client always processes the open-screen packet (and therefore Screen.init()) to completion before it even receives, let alone applies, the content packet."
    - "The existing GameTest suite (BindingAltarGameTests / BindingAltarMenuGameTests) only ever constructs a single server-side BindingAltarMenu directly (or via setupFullySocketedAltar's direct BE field injection) and asserts against menu.getDisplayedCandidates()/menu.getSlot() on that SAME server-side instance — it never constructs the separate CLIENT-side menu instance (empty at construction) the way a real ClientboundOpenScreenPacket handler would, so this exact timing bug was structurally unreachable by the existing suite."
  falsification_test: "Construct a BindingAltarMenu via the CLIENT constructor path (level.isClientSide() true) against a fully-socketed altar with a real non-empty server-side pool. If the client-constructed menu's candidate slots are non-empty at construction time (before any setAll/sync call), the hypothesis is false. Observed: they are List.of()/all-empty at construction, and only become populated after a subsequent AbstractContainerMenu#setAll(...) call mirroring the real content-sync packet — confirming the hypothesis."
  fix_rationale: "BindingAltarScreen (and PromotionRitualScreen, same reused pattern) must not treat the ONE synchronous init()-time slot read as final. The fix re-reads the candidate slots every client tick via containerTick() (already-overridable per AbstractContainerScreen, the same hook vanilla's own MerchantScreen family uses for exactly this 'server slot content hasn't synced yet' problem) and rebuilds the TradeCandidateList widget the moment the read result changes (i.e. once the content-sync packet has actually been applied) — this fixes the root cause (stale synchronous snapshot) rather than a symptom, and needs no new network payload (uses only the existing per-tick Screen lifecycle hook)."
  blind_spots: "Cannot directly exercise the real two-packet client network flow (ClientboundOpenScreenPacket then ClientboundContainerSetContentPacket) inside a GameTest, since GameTest runs server-side only with a mock player that has no real client connection/screen. The regression test therefore exercises the underlying AbstractContainerMenu mechanics (client-ctor menu starts empty, becomes populated only after setAll — the exact mechanism the screen-level bug depends on) rather than the full end-to-end packet sequence. PromotionRitualScreen shares the identical broken pattern; fixed as part of the same root-cause fix even though not explicitly reported by the user, since leaving it broken would reproduce the same symptom on the Promotion Ritual screen the next time a player levels up an employee."

actual: The Binding Altar screen opens but the trade candidate list is empty, showing the red "This position has nothing to offer yet. No trades are on file for this role." message, even for professions confirmed (via GameTest sweep) to have real non-empty tier-1 pools.

## Resolution

root_cause: "BindingAltarScreen#init() (and PromotionRitualScreen#init(), same reused pattern) builds its TradeCandidateList widget from a single synchronous read of the client-side menu's candidate slots, taken at Screen construction time. But the client-side BindingAltarMenu instance always starts with empty candidate slots (resolveDisplayedCandidates' client branch returns List.of() by design — the real per-slot data is meant to arrive via vanilla's normal container-content sync). Server-side, ClientboundOpenScreenPacket (which triggers the client's Screen/init()) is always sent and fully processed BEFORE the separate ClientboundContainerSetContentPacket that actually populates those slots arrives. So init() unconditionally reads all-empty slots and permanently bakes an empty candidate list into the widget, even though the server already rolled a correct, non-empty pool — on every real player-driven open, not intermittently."
fix: "Re-read the candidate slots every client tick via containerTick() (AbstractContainerScreen's existing per-tick hook) and rebuild the TradeCandidateList widget whenever the read result's size changes from what's currently displayed — this picks up the real synced data the moment the content packet actually applies, with no new network payload. Applied to both BindingAltarScreen and PromotionRitualScreen (identical root cause, identical fix shape; PromotionRitualScreen additionally needed its onSelectionChanged callback re-wired on rebuild)."
verification: "The true root cause (client Screen#init() timing) cannot be directly reproduced in a server-only GameTest — there is no real client connection/screen in that harness (confirmed empirically: routing BOTH real socket-fill clicks through SoulAltarBlock#useItemOn, which auto-opens the menu on the second click via sp.openMenu(...), throws 'Payload neoforge:advanced_open_screen may not be sent to the client!' against GameTestHelper's mock player — the BE mutation and server-side roll complete synchronously BEFORE that packet-send failure, so the two new tests catch that specific expected exception and then assert on the resulting BE state). Added two new GameTests exercising the real two-click useItemOn sequence for BOTH fill orders (soul-then-job, job-then-soul) confirming the server-side roll is — and remains — correct end-to-end via the real interaction path, not just the direct-BE-setter shortcut every prior test used. Full GameTest suite (90 pre-existing + 2 new = 92) run via ./gradlew runGameTestServer — all 92 passed, zero failures. ./gradlew compileJava run clean (only pre-existing deprecation warnings, no errors)."
