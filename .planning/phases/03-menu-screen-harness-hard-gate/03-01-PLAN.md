## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Client → Server menu-open request | The client never initiates a menu open this phase — server decides (D-01/D-02) and the client only receives `ClientboundOpenScreenPacket` |
| Client → Server menu-interaction packets | Vanilla `ServerboundContainerClickPacket` etc. against `BindingAltarMenu`, once the screen is open |
| World state → Menu validity | Altar block / job block can be broken while the menu is open |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-03-01 | Tampering | `BindingAltarMenu` (via vanilla `AbstractContainerMenu#clicked`) | mitigate | Only one custom `Slot` exists and it is display-only (`mayPickup`/`mayPlace` → false); vanilla's own slot-index bounds-checking in `clicked` rejects any out-of-range index — no additional code needed, verified by reading `AbstractContainerMenu` |
| T-03-02 | Tampering / Denial of Service | `BindingAltarMenu.stillValid` | mitigate | `stillValid()` delegates to the verified `AbstractContainerMenu.stillValid(ContainerLevelAccess, Player, Block)` static helper (block-identity + ~8-block distance), re-checked every server tick the menu is open; full D-12 forced-close messaging lands in Plan 02 |
| T-03-03 | Spoofing | Menu-open trigger | accept | No client→server "open this menu" payload exists this phase — the server alone decides to open via `serverPlayer.openMenu(...)`; the client can only receive, never request |
| T-03-04 | Information Disclosure | `BindingAltarScreen` / `AltarSoulContainer` | accept | The only data exposed is the already-visible socketed Soul Block item stack; no player-private data surfaced |
| T-03-SC | Tampering | Package installs | accept | No external packages (npm/pip/cargo) installed this phase — every class used is already-pinned `net.minecraft.*`/`net.neoforged.*` (RESEARCH.md Package Legitimacy Audit: not applicable) |
