<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Client → Server block-interaction packets | `useItemOn`/`useWithoutItem` right-click packets carry a claimed held item and hand — the server re-reads the actual server-side inventory stack, never trusts a client-declared item type |
| World state → Open menu | Altar block, job-site block, and player position can all change while `BindingAltarMenu` is open |
| Hand-crafted menu packets | A malicious client could send a `ServerboundContainerClickPacket`/button-click packet with an out-of-range index against the open `BindingAltarMenu` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|------------------|
| T-03-04 | Tampering | `SoulAltarBlock#useItemOn` | mitigate | `stack.is(ModItems.SOUL_BLOCK_ITEM.get())` reads the server-authoritative main-hand `ItemStack` from the event parameters, not a client-declared type; a spoofed "I'm holding a Soul Block" claim without the actual stack is impossible via the vanilla interaction packet, which always carries the real server-side item |
| T-03-05 | Tampering / Denial of Service | `BindingAltarMenu.stillValid` | mitigate | Job-block removal, altar removal, and player distance are all re-derived server-side every tick via `ProfessionResolver.fromAbove` + `AbstractContainerMenu.stillValid`; forced-close message + `false` return closes the menu — SC4's explicit acceptance criterion, covered by the `BindingAltarGameTests` suite |
| T-03-06 | Tampering | Hand-crafted out-of-range slot/button click against `BindingAltarMenu` | mitigate | Vanilla's own `AbstractContainerMenu#clicked` bounds-checks every slot index against `this.slots.size()`; the one custom `SoulSlot` is display-only (`mayPickup`/`mayPlace` false, set in Plan 01), so even a valid-index click on it is a no-op — no bespoke bounds-checking code needed this phase |
| T-03-07 | Repudiation / DoS | Forced-close message spam | mitigate | `forcedCloseMessageSent` guard ensures exactly one action-bar message per close, not one per failing tick |
| T-03-SC | Tampering | Package installs | accept | No external packages installed this task — `ProfessionResolver` uses only already-pinned `net.minecraft.*`/`net.neoforged.*` registries |

</threat_model>
