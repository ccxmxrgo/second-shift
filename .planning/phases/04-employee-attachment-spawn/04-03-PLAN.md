From CLAUDE.md §3 "Networking" (authoritative spec — no in-repo analog exists yet):
`playToServer`/`playToClient`/`playBidirectional` take `StreamCodec<? super RegistryFriendlyByteBuf, T>`
in the play phase. `IPayloadContext#player()` returns `Player`, not `ServerPlayer` — cast on the
server side. Handlers run on the main thread by default — do not set `executesOn(HandlerThread.NETWORK)`.
`PacketDistributor.sendToServer(payload)` sends from the client. Register via `RegisterPayloadHandlersEvent`
on the mod bus (this project has no existing call site for this event — add it to `SecondShift.java`
alongside the existing `modBus.addListener(this::commonSetup)` line, matching the "one visible wiring
point" discipline the class Javadoc already documents).

this codebase) — use `execute` for the bind handler's mutate-and-spawn body.

From content/block/SoulAltarBlock.java `useItemOn` (lines 101-133) — the validate-before-mutate
discipline to mirror: gate on server-side (`!level.isClientSide`), re-derive state from the BE
(never trust client input), mutate, `setChanged()`, `sendBlockUpdated(...)`.

From content/blockentity/SoulAltarBlockEntity.java — `isEmpty()`, `getHeldSoulBlock()`,

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Client (BindingAltarScreen Confirm button) → Server (ServerPayloadHandler) | Untrusted input: any client can send a `BindEmployeePayload` at any time, not just when a legitimate Binding Altar menu is genuinely open and valid server-side. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigate |
|-----------|----------|-----------|-------------|-----------------|
| T-4-01 | Spoofing / Elevation of Privilege | `ServerPayloadHandler.handleBindEmployee` | mitigate | The payload carries zero fields (D-01) — there is no client-supplied position to spoof. The handler re-derives the altar position exclusively from `sp.containerMenu`'s server-side `BindingAltarMenu` state (`menu.access()`), re-validated via `stillValid(sp)` before any mutation. A client cannot cause a spawn at an arbitrary position because no position ever crosses the wire. |
| T-4-02 | Repudiation / Resource exhaustion (minor, single-player) | `ServerPayloadHandler.handleBindEmployee` + `SoulAltarBlockEntity` | mitigate | The Soul Block slot's `isEmpty()` check and its `setHeldSoulBlock(EMPTY)` consume happen in the same synchronous `access().execute(...)` lambda invocation as the `EmployeeManager.bind` call, with no intervening logic — a second rapid Confirm click server-side sees an already-empty BE and no-ops before reaching `bind`. |
| T-4-03 | Tampering (unintended) | `sp.containerMenu instanceof BindingAltarMenu` check | mitigate | The handler checks the player's LIVE server-side `containerMenu` field, never a client-asserted "I have this menu open" claim — a client cannot fake having a different menu open than the server believes. |

</threat_model>
