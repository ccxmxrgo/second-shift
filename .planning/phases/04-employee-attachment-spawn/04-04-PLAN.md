    Run `./gradlew runClient` and work through this procedure (from 04-RESEARCH.md's "Manual
    Verification Procedure"):

    1. Place a Soul Altar, place a lectern (or any vanilla job-site block) on top, insert a Soul
       Block. Click "Confirm Hire". Note the spawned employee's UUID — target it and press F3, or
       run `/data get entity @e[type=minecraft:villager,name=<the shown name>,limit=1]`.
    2. Run `/data get entity <uuid>`. Confirm a `secondshift:employee` (or equivalent) attachment
       key appears under the entity's persistent data, with the expected name/profession/tier/offers
       populated — not empty/default values.
    3. Walk (or `/tp`) 300+ blocks away so the employee's chunk unloads, then return. Run `/data get
       entity <uuid>` again — confirm identical data survived the chunk-unload round trip.
    4. Run `/save-all`, fully quit the client, relaunch `./gradlew runClient`, reload the same
       world. Run `/data get entity <uuid>` again — confirm identical data survived the save/reload
       round trip.
    5. Check `logs/latest.log` (or the client console) for the `ClientEmployeeSyncDebug` log line
       (`"[SecondShift] client-side EmployeeData sync check: ..."`) printed at bind time and again
       after step 3/4's reloads. Confirm it shows the real populated `EmployeeData`, not the `EMPTY`
       default — this is the LIGHT spike's empirical answer.

       wild villager would (D-02) — no green color persists on the new name, no crash, no special
       behavior.
    7. Spawn or find a separate wild villager elsewhere in the same world (`/summon
       minecraft:villager`). Confirm: no green name, no custom name, normal vanilla trading/AI
       behavior, and (if a debug read is available) `hasData` false for it.
