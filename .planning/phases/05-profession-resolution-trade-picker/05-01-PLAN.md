<objective>
Replace the Phase 2-4 "place a real job-site block on top of the altar" mechanic with the locked
G-2 item-socket design (D-01): right-clicking a job-site item onto the altar consumes it into a
second block-entity slot, and the target profession is resolved from that socketed item via the
POI registry — not from a block placed at `pos.above()`. This plan also lands the full block-entity
data contract (job-item slot, one-employee-per-altar occupancy flag, transient session fields for
the trade candidates and default name) that every later plan in this phase builds against, and the
altar-occupied no-op behavior (D-04, ALTAR-05).

Purpose: G-2 is the same interaction surface as "how is profession determined" — building it now
(rather than adding real trade logic on top of the doomed block-on-top mechanic first) avoids
throwaway work and permanently retires Phase 4's `altarPos.above(2)` spawn workaround's root cause.
Output: `SoulAltarBlockEntity` with the full dual-socket + occupancy + session-data contract,
`ProfessionResolver.fromItem`, a fully rewritten `SoulAltarBlock` interaction surface, and
`BindingAltarMenu.stillValid` re-checking the new job-item slot instead of `pos.above()`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Player → Block interaction | `useItemOn`/`useWithoutItem` receive a client-triggered interaction; the held `ItemStack` and its resolved profession must only ever be trusted when computed server-side (`!level.isClientSide`) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-------------------|
| T-05-01 | Tampering | `SoulAltarBlock.useItemOn`/`useWithoutItem` | mitigate | All socket mutation, profession resolution (`ProfessionResolver.fromItem`), and occupancy checks run exclusively inside the `!level.isClientSide` branch — client-side interaction return values only drive rendering, never mutate BE state |
| T-05-02 | Elevation of Privilege | Altar occupancy (`employeeBound`) | mitigate | Checked as the FIRST branch in both `useItemOn` and `useWithoutItem` before any other logic runs, so no code path can socket an item or open a menu on an already-bound altar via any interaction sequence |
| T-05-03 | Tampering | Job-item stack validation | accept | A `BlockItem` with a spoofed/renamed display name still resolves its profession from the real underlying `Block`'s `PoiType`, not from item metadata — no spoofing surface exists here |
</threat_model>
