<objective>
Wire the real trade pool into the menu: the first time a `BindingAltarMenu` is constructed
server-side against an altar with both sockets filled, roll and store the profession's tier-1
candidates (via Plan 05-02's `TradePoolCache`) and a default employee name onto the block entity
(Plan 05-01's `candidateOffers`/`defaultName` fields) — exactly once per bind session, per
RESEARCH.md Finding 1's "generate once, store, reuse" policy. Expose accessors the real screen
(Plan 05-06) and the network trust-boundary handler (Plan 05-05) both read from.

Purpose: this is the seam between "the pool exists" (05-02) and "the pool is trustworthy
server-side state the client picks from" (05-05/05-06) — without it, either every menu-open would
re-roll (leaking orphaned map `SavedData` per Finding 1) or the screen/network layer would have to
duplicate the roll-once logic themselves.
Output: `BindingAltarMenu` with a populated, session-stable candidate list and the GUI-03 read
contract.
</objective>
